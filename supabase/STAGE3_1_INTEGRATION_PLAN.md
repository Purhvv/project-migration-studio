## 3. Рекомендуемая архитектура

```text
Публичная демонстрация
  существующие страницы -> queries.ts (demo) -> mock.ts

Личная область, только после отдельной реализации
  Auth SDK -> проверенная сессия -> защищённый маршрут
  экран -> queries.ts (account + userId)
        -> createServerFn + bearer middleware
        -> requireSupabaseAuth
        -> context.supabase (RLS пользователя)
        -> SELECT / shiftly_write(operationKey, action, payload)
        -> auth.uid() + ограничения + NUMERIC + аудит + транзакция

Привилегированные операции
  проверенный серверный обработчик
        -> отдельная авторизация задачи/владельца
        -> server-only admin client
        -> Auth Admin / служебный RPC
```

### 3.1. Публичное и защищённое

Существующую демонстрацию нельзя автоматически превращать в закрытый продукт или удалять. Предлагается оставить её URL и данные, а личной области дать отдельные именованные URL, например `/app/dashboard`, `/app/calendar`, `/app/profile`, под `_authenticated`. Это разные источники данных/режимы, а не публичное зеркало личных записей. Финальная карта URL согласуется на этапе реализации; не добавлять второй индекс `/` и не дублировать один публичный shareable-маршрут под защитой.

Для управляемого подключения использовать предоставляемый интеграцией `_authenticated/route.tsx`: клиентский gate (`ssr: false`), проверка `getUser()`, переход на публичный `/auth`. Наличие и фактическое поведение созданного scaffold нужно прочитать после подключения, прежде чем дополнять его. Не писать второй guard в каждом дочернем экране.

Причина: рекомендованная SDK-сессия хранится в браузере, серверный SSR не видит её localStorage. Protected loaders запускаются только в защищённом клиентском поддереве. Публичные SSR-загрузчики не вызывают функции с обязательным Auth. `ssr: false` применяется только к приватному поддереву, не ко всему приложению.

### 3.2. Серверные функции и RLS

- Внутренние чтения/записи: `createServerFn`, не Supabase Edge Functions и не чувствительные операции прямо в loader.
- `src/start.ts`: добавить существующий/сгенерированный `attachSupabaseAuth` в `functionMiddleware`, сохранив error/CSRF middleware и любые уже существующие middleware. Не дублировать attacher.
- Каждый личный handler: `.middleware([requireSupabaseAuth])`. Проверка bearer выполняется сервером; клиентские claims, `userId` из формы, URL или localStorage не являются полномочиями.
- Использовать `context.supabase`, `context.userId`, `context.claims`. SELECT ограничен RLS, записи идут в `public.shiftly_write(p_key uuid, p_type text, p_payload jsonb)`. В базе личность заново выводится из `auth.uid()`; не принимать произвольного владельца.
- Route guard — удобство навигации; прямой вызов RPC/serverFn также обязан получить 401/403 без права доступа. Сохранить CSRF; он не заменяет Auth/RLS.
- `SECURITY DEFINER` у финансового RPC не даёт право доверять payload: финальная БД проверяет владельца, ключ операции, ревизии, allowlist, конфликты и денежные строки.
- Точное действие изменения профиля — **`profile_edit`**, не `profile_update`; payload содержит `expected_revision` и только разрешённые поля. Email изменяется через Auth, не через таблицу профилей.
- Не пересылать вычисленные клиентом earnings/commission в качестве истины. Канонические десятичные строки/NULL на границе записи; на сервере NUMERIC. Для чтения нужен будущий DTO, исключающий потерю точности JSON-number при финансовых сверках; существующие UI Number не должны становиться серверным расчётом.
- Для скрытых/удалённых данных использовать owner-scoped чтение и отдельные active/trash запросы. Идентичность, источник данных и месяц/место работы входят в ключи кэша.
- Приватные ответы — `no-store` либо корректно приватное кэширование; никакого общего CDN-кэша пользовательских ответов и токенов в DTO.
- Server-only admin module загружается внутри проверенного handler, не верхнеуровневым импортом из страницы или клиентски достижимого `.functions.ts`. Обычные чтения/записи не используют service_role.

### 3.3. Не смешивать демонстрацию и аккаунт

Будущие ключи запросов должны различать `demo` и `account`, а также userId. Переключение режима/аккаунта очищает старый кэш. При 401, отсутствии профиля или сбое сервера **нельзя незаметно подставить mock**: пользователь должен видеть ошибку входа/данных, а не чужой демо-профиль. Никакого переноса `u1/w1/s1`, демонстрационных денежных остатков и выдуманных ставок автоматически.

Адаптер БД и DTO размещаются под существующим шлюзом `queries.ts`; приложение сейчас не переписывается. Позже потребуются отдельные согласованные изменения для UTC/IANA, revision, версий, fixed_pay и строгой машины статусов: комментарий `types.ts` о совпадении с будущими таблицами не является гарантией совместимости.

## 5. Auth и безопасная сессия

### 5.1. Выбор механизма

Рекомендация: единственный клиент SDK в браузере, стандартное persistSession/autoRefreshToken и управляемое хранилище SDK. Access/refresh token не копируются вручную в cookie, Redux, query cache или другие localStorage-ключи. Для bearer-attacher допустим `getSession()`; для доверенной проверки входа — `getUser()` и серверная проверка bearer.

Это **не HttpOnly-защита**: SDK-сессия в localStorage доступна JavaScript и уязвима при XSS. Меры: не выводить недоверенный HTML, контролировать внешние скрипты, применять совместимую CSP, не отправлять токены в аналитику/логи/URL, проверять redirect и очищать секреты recovery из адреса после обработки. CSP нужно сначала проверить с текущим Start/preview/OAuth, а не включать вслепую.

Cookie-based SSR с `@supabase/ssr` — альтернативная архитектура, не параллельный механизм «на всякий случай». Она потребует полноценного request-scoped cookie adapter, обновления токенов в response, PKCE/callback и CSRF-проверок. Само применение `@supabase/ssr` не гарантирует HttpOnly. Такой переход отдельно согласуется и сейчас не требуется.

В корне регистрируется одна подписка `onAuthStateChange` с cleanup. Реакция на `SIGNED_IN`, `SIGNED_OUT`, `USER_UPDATED`: инвалидировать Router; query refetch — только не на SIGNED_OUT. Не превращать `TOKEN_REFRESHED` и `INITIAL_SESSION` в массовый сброс/перезагрузку. Начальная сессия отдельно гидратируется и проверяется до личного loader.

### 5.2. Сценарии доступа

| Сценарий | План поведения | Проверка |
|---|---|---|
| Регистрация email/password | реальный email, пароль, имя; `signUp`, redirect на same-origin публичный URL | при включённом подтверждении `session === null`: показать ожидание письма, не считать вошедшим |
| Подтверждение email | SDK обрабатывает callback, затем сервер проверяет сессию | неподтверждённый/просроченный код не открывает личные данные |
| Вход | `signInWithPassword`, проверка пользователя и готовности профиля, безопасный переход | email — credential; имя профиля не используется для поиска чужого email |
| Социальный вход | при управляемом подключении Google через `lovable.auth.signInWithOAuth`, не raw Google OAuth | публичный same-origin callback, затем проверка сессии и переход |
| Вход через Lovable | предусмотреть для управляемого Auth наряду с email/password и Google | доступность и фактический способ вызова подтвердить после подключения |
| Выход | cancelQueries → clear cache → `signOut` → переход `/auth` с replace | Back/обновление/другая вкладка не показывают личный кэш |
| Забытый пароль | `resetPasswordForEmail`, redirect `${origin}/reset-password` | одинаковое сообщение для существующего/несуществующего email; не раскрывать аккаунты |
| Сброс пароля | публичный `/reset-password`, обработка recovery (включая `type=recovery` в hash/SDK callback), новый пароль | `updateUser({ password })`, без current_password; недействительная recovery-сессия отклоняется |
| Изменение пароля после входа | текущий и новый пароль | `updateUser({ password, current_password })`; не смешивать с recovery |
| Истёкшая/отозванная сессия | SDK обновляет; при окончательном 401 очистить личные данные и запросить вход | никаких бесконечных retry и fallback на demo |

Методы входа — предлагаемая конфигурация, не уже включённые настройки. Email/password на новом управляемом проекте может быть выключен: при реализации обязательно явно включить его соответствующим инструментом; социальные провайдеры также включаются отдельно. Автоподтверждение email не менять без согласия. Проверить парольную политику, HIBP и требование текущего пароля; сейчас они не установлены и не проверены.

Redirect allowlist задаётся отдельно для разрешённых preview/production адресов; не доверять произвольному `redirect` из query. Хранить только проверенный same-origin путь назначения, не access token. OAuth возвращается на публичную страницу, не сразу под protected gate. Управляемый helper обеспечивает вход в iframe-preview; не писать обход через самостоятельно открытое окно.

## 6. Автоматическое создание профиля

Наличие профиля уже однозначно требуется задачей и моделью v3. Дополнительные таблицы или роли не нужны.

Существующий `public.profiles` (`20261108140000_v3_schema.sql`): `id` с FK на `auth.users(id) ON DELETE CASCADE`; обязательное непустое `name`; `currency='RUB'`, `timezone='Europe/Moscow'`; nullable цели; `revision=1`, timestamps. Email, аватар и роли в эту таблицу не добавляются: email принадлежит Auth. Табличные записи клиенту запрещены, поэтому INSERT после signup в браузере — неверный механизм.

### 6.1. Будущая новая forward-миграция, не реализация сейчас

Предлагается **после отдельного разрешения** добавить десятую migration-only операцию: функцию provision profile и `AFTER INSERT ON auth.users` trigger. Девять существующих файлов не переписывать. Модель остаётся ровно из 12 таблиц.

Контракт функции:

1. `NEW.id` — единственный источник идентификатора; пользовательский payload/metadata не задаёт владельца.
2. В той же транзакции вставить одну строку существующего `profiles`.
3. Выбрать непустое безопасное имя из разрешённого поля регистрации/провайдера; metadata недоверенны. Ограничить длину и обработать отсутствие/неверный тип. Для OAuth без имени предлагается нейтральное резервное имя, не email/его часть; точный текст согласуется в реализации.
4. Currency/timezone использовать существующие defaults; не переносить произвольные metadata в цели, роли или финансовые настройки. Если пользователь позже меняет timezone, делать это через валидированный `profile_edit`.
5. Идемпотентность `ON CONFLICT (id) DO NOTHING` — без перезаписи уже настроенного профиля при повторном provision.
6. `SECURITY DEFINER`, квалифицированные имена, фиксированный безопасный search_path, владелец с необходимым INSERT, REVOKE EXECUTE от PUBLIC/anon/authenticated. Не выдавать клиенту INSERT на profiles и не делать таблицу публичной.
7. Ошибка provision откатывает регистрацию: не подавлять её и не оставлять «успешный» аккаунт без профиля. Логировать только безопасную диагностику.

Триггер сработает при создании Auth-строки, обычно до подтверждения email; это не означает вход пользователя. Для старых Auth-пользователей автоматический INSERT trigger задним числом не сработает: при необходимости отдельный разрешённый идемпотентный backfill отсутствующих профилей, без перезаписи имеющихся и без выдумывания исторических финансов.

### 6.2. Проверки provision

- Реальные signup/email confirmation и OAuth в разрешённой отдельной среде: один Auth ID → одна строка profiles.
- Отсутствующее/пустое/вредоносное имя; правильные defaults и nullable цели, не демо-цели.
- Повтор provision не меняет имя/цели/revision, настроенные пользователем.
- При ошибке trigger нет частично созданного аккаунта; сообщение пользователю не содержит SQL/секретов.
- Пользователь читает только свой профиль и меняет его через `profile_edit` с ожидаемой ревизией; прямой DML запрещён.
- Удаление Auth-аккаунта очищает профиль и связанные данные; второй пользователь не затронут.

## 7. Порядок подключения и тестирования

### 7.1. Шаги, каждый вне текущей реализации

1. Получить отдельное разрешение на тестовую среду и точный объём следующего этапа. При управляемом подходе включение Cloud создаст инфраструктуру; этого сейчас не делать. Если пользователь отдельно выбирает свой сервис, его соединение выполняется в настройках Lovable, не имитацией вручную созданных integration-файлов.
2. До любых данных проверить snapshot/backup и восстановление, актуальные Auth/grants, наличие `auth.users`, `auth.uid()`, `gen_random_uuid()`, права владельца функций и доступность public/private schema. В миграциях нет установки расширений; UUID-функция в актуальном PostgreSQL штатная, но её наличие всё равно проверяется.
3. Сохранить контрольные суммы/историю девяти исходных migrations, выполнить тестовое применение **в порядке ниже** без cherry-pick. Частично применённая схема не обслуживает приложение. Учёт выполненных миграций вести инструментом миграции; повторный CREATE-пакет без отката не предусмотрен.
4. После отдельно разрешённой реализации новой migration профиля проверить её поверх полного пакета. Не включать публичную регистрацию раньше рабочего provision. Стандартный generated scaffold не должен создавать альтернативную таблицу profiles, переписывать её схему или расширять прямые grants.
5. Сгенерировать Database types, проверить реальные integration-файлы и bearer middleware; выполнить Auth- и serverFn-проверки в отдельной интеграционной среде. Демо остаётся независимым.
6. Подключение адаптера `queries.ts`, экраны аккаунта, перенос данных и месячные задания — самостоятельные следующие задачи, не скрытая часть этапа 3.1.
7. Перед рабочим применением: разрешение, backup/PITR и восстановление, закрытие необходимых блокеров, полный протокол тестов. Обратные .down.sql на пользовательских данных запрещены: они удаляют таблицы; восстанавливать backup.

### 7.3. Два разных вида тестовых сред

**Локальная одноразовая PostgreSQL 17.11:** воспроизводит сохранённые SQL-сценарии с минимальным Auth-каркасом. Роли и `auth.users/auth.uid` нужно подготовить до migration 1: её FK/RLS уже зависят от них. Сохранённый scenario-файл содержит свой дополнительный каркас, но не является установщиком предпосылок миграций.

Будущий порядок запуска, только при отдельном разрешении; команды ниже в этом этапе не выполнялись:

```sh
# TEST_DB_DSN должен указывать только на явно проверенную локальную одноразовую БД.
# Здесь намеренно нет команды применения миграций к произвольной рабочей среде.
psql "$TEST_DB_DSN" -v ON_ERROR_STOP=1 -f supabase/tests/v3_contract.sql
psql "$TEST_DB_DSN" -v ON_ERROR_STOP=1 -f supabase/tests/v3_1_contract.sql
PGOPTIONS='-c app.shiftly_test_env=on' psql "$TEST_DB_DSN" -v ON_ERROR_STOP=1 -f supabase/tests/v3_1_scenarios.sql
# Concurrency использует только отдельную marked clone-базу; она будет уничтожена.
SHIFTLY_LOCAL_TEST_CONFIRM=DESTROY_DISPOSABLE_LOCAL_DATABASE PGOPTIONS='-c app.shiftly_test_env=on' TEST_CLUSTER_DIR=<local-cluster> TEST_DB_NAME=<disposable-clone> TEST_DB_PORT=54399 bash supabase/tests/v3_1_concurrency.sh
```

Контрактные файлы проверяют каталог/валидаторы, scenario — 11 последовательных сценариев в транзакции с ROLLBACK, shell — 3 реальные конкурентные проверки. Все требуют отдельного безопасного назначения; scenario дополнительно проверяет GUC и пустые public-таблицы.

**Находка аудита устранена отдельной работой 09.11:** concurrency harness больше не заменяет Auth, требует независимое внешнее подтверждение, закреплённый /tmp Unix socket и read-only preflight фактических параметров/ролей/пустоты/hosted-маркеров до записи. GUC не доказательство локальности. После preflight всю clone-базу удаляет cleanup; внешний владелец обязан уничтожить и кластер, особенно при SIGKILL/сбое cleanup. Arbitrary DSN запрещён. Три повторных раунда и регрессии отказов/error/INT/TERM описаны в STAGE2_REPORT.md. **Ни один локальный auth-shim harness нельзя запускать на настоящем Auth-проекте, даже пустом.**

После SQL-прогона проверить 0 business rows/тестовых ролей и отсутствие остатков; завершение shell с кодом 0 не заменяет сверку. В чистой локальной базе: 9 down в обратном порядке → 9 forward → контракты. При проверке будущего provision использовать отдельный вариант harness/БД: существующие фикстуры сами вставляют profiles и могут конфликтовать с новым signup-trigger. Не менять сохранённые исходные migrations ради этого.

**Отдельная настоящая интеграционная тестовая среда после разрешения:** реальный Auth, SDK, Data API/RLS, serverFn и опубликованное приложение. Здесь **не запускать** локальные auth-shim сценарии. Создать отдельно разрешённые тестовые аккаунты обычным signup и проверить через реальный HTTP/JWT, затем удалить их контролируемо. Наличие этапа 2.1 не доказывает прохождение этого набора.

### 7.4. Матрица интеграционных проверок

- Два реальных тестовых пользователя: чтение своего профиля/смен и ноль чужих; подмена userId/UUID/workplace не даёт доступа.
- Прямой вызов приватного serverFn без токена, с истёкшим/неверным токеном → отказ; обычные операции идут под JWT пользователя, не admin.
- Auth lifecycle: регистрация → подтверждение → вход → профиль → реальная запись → чтение через UI → выход → Back/обновление. Отдельно OAuth, recovery, смена пароля и отзыв/истечение сессии.
- Прямой клиентский INSERT/UPDATE/DELETE всех 12 таблиц запрещён; разрешённые RPC работают с владельцем и ревизией. Идемпотентность/ошибка/конкурентность — реальная запись и повторное чтение.
- Private cache: смена аккаунта/режима и выход не показывают данные предыдущего пользователя; SSR публичной демонстрации не содержит личных записей.
- Финансы/время: NULL не 0; exact cents; independent workplace/month; fixed_pay один раз; DST, expected_revision, trash/restore и конфликт override. Прогнозы не включают неподтверждённые комиссии.
- Административное удаление: повторная подтверждённая идентичность владельца, Auth Admin delete → `shiftly_delete_account` → сверка очистки; отказ неподходящему caller, безопасный retry. Нельзя разрешить пользователю произвольный UUID цели.
- Разделение env, bundle и телеметрия: браузер не содержит service_role/refresh token в ответах или логах; opaque publishable key не передан как JWT; request-scoped серверные клиенты, private/no-store responses.
- Текущие `bunx vitest run` — регрессия демонстрации; автоматическая сборка и настоящая опубликованная проверка серверных функций обязательны позже. Локальный dev не доказывает работу опубликованного окружения.

## 9. Нерешённые вопросы и границы готовности

Из `STAGE2_REPORT.md` сохраняются отложенными: исторический `confirm_history` без защищённого preview-контракта и смена workplace timezone с историей. Утверждено: обе денежные цели NUMERIC(14,2); один rate_interval_id на одну смену только один раз, UNIQUE(shift_id, rate_interval_id). Эти два вопроса закрыты. Базовый Auth можно проектировать при безопасном запрете отложенных операций; рабочее применение/запуск требует закрытия относящихся к нему вопросов.

SQL уже имеет служебный local-month close, но **расписания автообнуления и очистки корзины не установлены**. Настройка scheduler/API с проверкой caller и идемпотентностью — отдельная реализация, не часть регистрации. Account deletion orchestration и обязательный до публичного запуска CSV также не реализованы.

Строгая nested JSON validation и Largest Remainder исправлены в этапe 2.1; ранние пункты исходного отчёта о них нельзя считать актуальными дефектами финального пакета. С другой стороны, прежние локальные успешные сценарии не заменяют реальные Auth/PostgREST/серверные HTTP-тесты.
