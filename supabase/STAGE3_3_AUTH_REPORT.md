# Этап 3.3 — авторизация Shiftly

## Реализовано

- `/auth`: вход email/пароль, безопасные сообщения ошибок, повторное письмо подтверждения.
- `/register`: имя, email, пароль и повтор; без сессии после signup показано ожидание подтверждения.
- `/auth/callback`: публичное завершение подтверждения и переход в `/account`.
- `/forgot-password`: письмо восстановления без раскрытия существования аккаунта.
- `/reset-password`: новый пароль только для recovery-ссылки/сессии; затем завершение сессии и новый вход.
- `/account`: отдельная защищённая клиентская зона, чтение только собственного существующего профиля через серверную функцию, выход.
- В публичном `/profile` добавлена ссылка «Войти в Shiftly» / «Личный аккаунт» по состоянию сессии.
- SDK сохраняет/обновляет сессию. Единственная root-подписка очищается при размонтировании; смена личности и выход удаляют account-кэш. Проверка пользователя при возвращении во вкладку и раз в минуту обнаруживает недействительную сессию.
- Сервер: bearer middleware, дополнительный `getUser()` и проверка подтверждённого email; id профиля берётся только от проверенного пользователя. CSRF/error middleware сохранены. Серверный QueryClient создаётся отдельно для каждого router, не глобально.

Публичное демо, главная, нижняя навигация, SQL, mock.ts, queries.ts, финансовые таблицы/RPC и формулы не изменены. Зависимости не устанавливались. Service role не используется.

## Как проверить вручную

Используйте собственный доступный почтовый ящик, а не демо-пользователя; откройте preview отдельной вкладкой.

1. Профиль → «Войти в Shiftly» → «Создать аккаунт». Введите имя, email и два одинаковых пароля.
2. До подтверждения появится сообщение о письме; `/account` без подтверждённой сессии недоступен.
3. Откройте ссылку в письме: `/auth/callback` завершит подтверждение и откроет `/account`. Имя должно прочитаться из профиля, созданного SQL-триггером, а не демо.
4. Перезагрузите `/account`: сессия сохраняется. Выйдите и проверьте, что Back/прямая ссылка не открывают приватный профиль.
5. Войдите email/паролем. Неверный пароль должен дать понятную ошибку без деталей Supabase.
6. «Забыли пароль?» → отправьте письмо → откройте ссылку → задайте новый пароль дважды. Войдите заново новым паролем. Простое открытие `/reset-password` без recovery-ссылки не разрешает изменение.
7. Завершите/отзовите сессию и вернитесь во вкладку: приватный аккаунт должен потребовать новый вход; публичное демо остаётся доступно.

## Проверки и ограничения

Существующие 91 тест прошли. Добавлены 6 тестов правил Auth: ожидание подтверждения, адрес recovery, несовпадение паролей, запрет reset обычной сессией, recovery update без current_password, отсутствие raw ошибок.

Браузер: прямой `/account` без сессии переходит на вход; reset без письма заблокирован; ссылка входа из демо доступна; мобильный экран без горизонтального переполнения. Новые экраны осмотрены. Автоматическая сборка после исправления ошибок прошла.

Реальная регистрация, получение письма, подтверждение, authenticated read профиля и смена пароля через подключённый Supabase end-to-end не проверены: внешний проект не предоставляет управляемую тестовую сессию, создавать демо-пользователей запрещено. Это не заменено проверкой пустого аккаунта. Полный поток необходимо проверить собственным реальным аккаунтом по шагам выше.
