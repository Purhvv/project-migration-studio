# Shiftly — отчёт Этапа 2: SQL v3

Дата: 08.11.2026. Статус: офлайн-пакет подготовлен и проверен по структуре; **не готов к применению в рабочей базе до закрытия указанных блокеров**.

## Границы

Cloud не подключён. Рабочая база не использовалась. `src/`, страницы, компоненты, дизайн, `mock.ts` и `queries.ts` не изменены. Нет INSERT с демо-данными и нет дополнительных пользовательских таблиц. До работы папка `supabase` отсутствовала. Использованы финальная модель v3 и утверждённая дельта аудита v3.1 (комментарий премий/штрафов, первый порог 0, составные UNIQUE, уникальная дата версии).

## Что создано

5 последовательных миграций, 5 обратных файлов, SQL-проверки без строк данных и два документа. Полный перечень — ниже.

### Таблицы

`profiles`, `workplaces`, `operation_requests`, `rate_versions`, `rate_intervals`, `commission_rule_versions`, `commission_thresholds`, `shifts`, `shift_adjustments`, `shift_fixed_payments`, `monthly_commission_results`, `shift_financial_events`.

У каждой таблицы: PK, необходимые FK, GRANT сразу после CREATE TABLE, RLS и owner-read политика. Клиентские INSERT/UPDATE/DELETE запрещены на всех таблицах. Деньги — NUMERIC с точностью из словаря данных; NaN отклоняется. NULL сохраняет смысл неизвестной суммы. Отрицательный заработок разрешён.

Результат проверенного каталога PostgreSQL: **12 таблиц, 12 RLS-политик, 29 FK, 11 прикладных триггеров, 15 SQL/PLpgSQL функций**. Создана только вспомогательная схема `shiftly_private`, не дополнительная таблица.

### Финансовые и защитные операции

- Заработок: base + fixed + commission + tips + bonus − penalty; неизвестный компонент даёт NULL. Фиксированные выплаты суммируются из снимков, а не добавляются в base второй раз.
- Фактическая почасовая оплата: elapsed time, одно округление в конце; отсутствие/перекрытие ставок даёт NULL, ставка-победитель не выбирается.
- Комиссия по конкретному месту и локальному месяцу; достигнутый процент применяется ко всей известной выручке. Целые копейки сначала отбрасываются вниз, остаток округлённого месячного итога назначается первым K сменам с известной выручкой в UUID-порядке. Неизвестная выручка не участвует в распределении; режим none даёт 0 комиссии.
- Месяц без неизвестной выручки — final по полноте, а не по запрету редактирования. `closed_at` сохраняет первое закрытие, поздние исправления разрешены.
- Автообнуление: только активные completed с NULL, после абсолютной границы следующего локального месяца; флаг, revision, аудит, пересчёт одной транзакцией. Только service_role; расписание не установлено.
- Идемпотентность и expected_revision/revenue_revision; ошибка откатывает всю RPC. Перенос между местами/месяцами пересчитывает обе стороны.
- Корзина: 720 часов (30×24); восстановление с конфликтным guard, purge с явным подтверждением. Снимки аудита редактируются исключительно контролируемой очисткой после purge; идентификатор subject_shift_id остаётся без FK.
- Опубликованные родители и дочерние строки защищены; публикация проверяет первый порог 0, форму правил, наличие интервалов и подтверждение пересечений. Удаление аккаунта допускает каскад при уже удалённой auth.users строке.

## Проверка SQL — что действительно выполнено

Проверено локальным PostgreSQL **17.11**, изолированным Unix-сокетом в `/tmp`, без TCP и без подключения проекта. В пустой локальной базе созданы только инфраструктурные заглушки ролей/auth.uid/auth.users и структура миграций. **Ни одной строки пользователя, места, смены, ставки или операции не создано.**

1. Все 11 SQL-файлов разобраны PostgreSQL-парсером pglast: синтаксических ошибок нет.
2. Все 5 миграций успешно применены на пустой локальной схеме; сервер принял CREATE FUNCTION/триггеры/FK/индексы.
3. Выполнены 10 DO-блоков: каталог/права, контрольная формула 2000+1000=3000, отрицательный итог −400, NULL-комиссия, NULL-base, half-up 0.005→0.01, DST elapsed=10800 секунд, Москва: 01.11 локально = 31.10 21:00 UTC, отказ без входа, все таблицы остаются пустыми.
4. Все 5 обратных файлов успешно выполнены в обратном порядке.
5. Все миграции повторно успешно применены после отката, все 10 блоков снова прошли.
6. Автоматическая проверка Preview: build OK; код интерфейса не менялся.

**Ограничение проверки:** PostgreSQL лениво планирует SQL внутри PLpgSQL. Успешное создание функции и проверка пустой схемы НЕ доказывают выполнение каждой ветки. Без тестовых строк не проверены реальные изменения смен, первая публикация, межпользовательская изоляция на двух аккаунтах, конфликт revisions, параллельные транзакции, распределение комиссий на записях, purge/redaction и cascade аккаунта. Для этого требуется отдельное разрешение на изолированные тестовые данные. Supabase-hosted Auth/PostgREST/workerd не проверялись и не подключались. Повторное применение миграций без отката не предусмотрено: это обычные одноразовые миграции; повторные операции идемпотентны через ключи.

## Противоречия и блокеры — модель самостоятельно не менялась

1. **Цели:** общая фраза v3 относит цели к numeric(18,2), но словарь profiles.monthly_goal/workplaces.revenue_goal явно указывает numeric(14,2). В SQL сохранён точный словарь numeric(14,2); нужен окончательный выбор диапазона перед рабочим применением.
2. **Даты версий:** v3 перечисляет UNIQUE(workplace,effective_from,revision), аудит v3.1 требует дополнительно UNIQUE(workplace,effective_from). Реализованы оба; более строгий запрет одинаковой даты — из утверждённого аудита, не новая интерпретация.
3. **Неизменяемость и очистка:** абсолютный запрет UPDATE/DELETE в аудите конфликтует с требованием очистки снимков purge и удаления аккаунта. Добавлено узкое исключение: только детерминированная очистка после отсутствия смены, либо cascade после удаления auth.users; бизнес-суммы/идентичность события не переписываются. Требуется сценарная проверка на данных.
4. **Исторический пересчёт:** предусмотрен confirm_history, но нет точного контракта защищённого preview (диапазон, снимок revision/digest, привязка подтверждения к новой версии, срок действия). Эту ветку **не реализовано**; ретроактивная публикация для периодов с completed отклоняется безопасно. Нельзя считать этот пункт этапа закрытым; реализация ждёт согласования контракта, а не придумывает его.
5. **Изменение часового пояса:** история хранит snapshot, а автообнуление использует текущий workplace.timezone. Политика закрытия старого месяца после изменения пояса не задана. SQL отклоняет изменение при наличии смен до согласования; существующие даты не переносит.
6. **Исходный проект:** нет UUID пользователей, истории ставок, fixed_pay, UTC/IANA, серверного финконтура и входа. Демо basePay включает выдуманную комиссию; исходные Number и ручной подтверждённый остаток нельзя безопасно импортировать автоматически. Адаптер/перенос и подключение экранов не выполнялись.
7. **Профили/Auth:** нет автоматического создания profiles при signup. Это следующий этап авторизации; до его реализации пользовательские RPC не смогут работать с новым аккаунтом без профиля.
8. **JSON-контракт:** денежные поля верхнего уровня требуют десятичные строки; вложенные интервалы/пороги/adjustments пока приводятся к NUMERIC напрямую. До подключения клиента необходим единый строгий рекурсивный валидатор с отказом для лишних/неправильно типизированных полей.
9. **Рабочая полнота:** не установлены задания автообнуления/очистки корзины, не реализованы API удаления аккаунта и CSV; это не запуск системы. Права service_role предполагают доверенный сервер, не пользовательский ключ.
10. **Производительность:** почасовой расчёт посекундный, точный, но линейный по длительности; до рабочей нагрузки нужна проверка и оптимизация по границам интервалов/DST без изменения результата.
11. **Дополнительное ограничение выбора fixed:** UNIQUE(shift_id,rate_interval_id) защищает от повторного назначения источника, однако v3 явно не определяет, допускается ли несколько одинаковых фиксированных выплат. Требуется подтверждение этой уникальности до применения; никаких новых таблиц/полей она не добавляет.

## План безопасного применения и отката

Не запускать пакет в рабочей базе сейчас. Сначала согласовать блокеры, разрешить тестовые сценарии на отдельной базе, проверить RLS/конкурентность/аудит/каскады и финансовую сверку. После отдельного разрешения: контрольная резервная копия, проверка восстановления, применение в ascending order. Обратные SQL — только для пустой тестовой схемы: они удаляют таблицы. При пользовательских данных — восстановление проверенного backup/PITR; технический down не заменяет восстановление.
