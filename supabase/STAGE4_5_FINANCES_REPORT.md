# Shiftly — этап 4.5

## Расчёт
- Существующие `shiftly_private.earnings`, `refresh_earnings`, `recalculate_month` переиспользованы, не переписаны: NUMERIC base_pay + fixed_pay + commission_pay + tips + bonuses − penalties. Выручка в итог не входит. NULL необходимого компонента оставляет полный итог NULL; отрицательное значение разрешено.
- Новое чтение `shiftly_confirmed_earnings` считает частичную сумму в PostgreSQL NUMERIC, не JS float, с owner-фильтром auth.uid() и существующим RLS (SECURITY INVOKER). Не сохраняет частичную сумму вместо payroll. Штрафы вычитаются даже при неизвестных остальных компонентах. Предварительное состояние месяца помечает также смены с известной выручкой.
- Чтение подключено только к деталям финансов смены; главная, статистика, графики и их существующий read-side helper не изменены в этапе 4.5. Перевод остальных финансовых чтений/агрегаций на NUMERIC остаётся объёмом 4.6, поэтому утверждение «всё приложение без JS float» сейчас неверно.

## Месячная комиссия
- Существующие none/fixed/thresholds и Largest Remainder: достигнутый процент со всей известной выручки; сумма распределённых копеек равна месячному NUMERIC-итогу.
- completed + активные строки, отдельное рабочее место и local_start_date месяца рабочего места. NULL не считается нулём; missing_revenue_count сохраняется. При missing > 0 состояние preliminary, при отсутствии неизвестной выручки final. calculation_available=false отдельно означает отсутствие правила; final не означает наличие всех прочих компонентов заработка.
- shiftly_write уже пересчитывает исходный и новый workplace/month при переносе, а также создание/завершение/правку/soft-delete. Эти механизмы не дублировались.

## Автоматическое закрытие
- pg_cron был доступен, но не установлен. Установлен и зарегистрирована одна активная SQL-only задача `shiftly-close-due-months`, `0 * * * *`: 24 проверки в сутки, обычная задержка до часа относительно местной границы месяца. Ежечасная проверка расходует ресурсы даже при отсутствии работы; не зависит от открытия приложения и не вызывает HTTP.
- `close_due_months` выбирает завершившиеся месяцы в timezone каждого workplace, включая пропущенные закрытия и поздно добавленные неизвестные смены прошлых месяцев. За запуск максимум 200 workplace/month; при большей очереди задержка увеличивается. Ошибка одного месяца записывается WARNING (без пользовательских сумм), остальные продолжаются; проблемный месяц остаётся для следующего запуска.
- `shiftly_close_month` теперь берёт owner/month locks до row locks и не создаёт повторное month_close при закрытом месяце; закрытый месяц без новых NULL возвращается без записей. Только completed, non-deleted NULL выручка получает 0/флаг/ревизии/аудит. Плановые смены и ручные суммы не затрагиваются. Новые закрытия используют существующие operation_requests и транзакционный пересчёт.
- Hosted проверка подтверждает активную задачу и отсутствие прямого исполнения закрытия пользователями. На момент проверки просроченных completed NULL смен было 0; реальный запуск по часам ещё не наблюдался.

## Поздняя коррекция
- Существующие shift_edit/revenue_correct допускают реальную decimal-строку с обеими ревизиями; база пересчитывает комиссию и итог.
- Текущая модель CHECK (NOT revenue_auto_zeroed OR revenue=0) означает, что флаг относится к текущему значению: при коррекции он очищается. Исторический факт обнуления сохраняется в before_snapshot события revenue_correction и отдельном auto_zero_revenue. Схема/ограничение не ослаблены.

## Целевые проверки
- 16 тестов (account-finance-read, account-finances, personal-finances, account-write-boundary) прошли; автоматическая сборка build OK.
- Новый stage4_5_finances.sql выполнен на отдельной пустой локальной PostgreSQL 17.11. Проверены конкретные NUMERIC-итоги 25250, предварительная комиссия 22500 при 1500000 × 1.5%, NULL, закрытие только completed, повторные ключи и разные ключи без повторных событий, исправление 500000 → общий месяц 2000000 × 2% = 40000, удаление → 22500, перенос в другое workplace/month, отрицательный итог −60, owner isolation, разные локальные даты границы и отказ текущего месяца, повтор задачи без изменений.
- Сценарии завершились ROLLBACK; тестовая база и весь кластер удалены. Hosted pg_cron установка проверена отдельно; локально этот установочный фрагмент пропущен, бизнес-функции применены без изменения. Concurrency harness и полный аудит не запускались.
- Реальные сохранения через браузер внешнего Supabase не проверены: управляемая сессия отсутствует. Synthetic hosted строки не создавались.
- Два прежних предупреждения не появились из-за этих миграций: предусмотренный SECURITY DEFINER RPC для authenticated и отключённая защита от скомпрометированных паролей. В текущем этапе не изменялись; могут быть рассмотрены отдельно.
