## 3. Совместимость: условная, не подтверждённая на target

Статические признаки совместимости: SQL использует PostgreSQL/PLpgSQL, NUMERIC, стандартные UUID/JSONB, RLS и Supabase Auth (`auth.users`, `auth.uid()`, роли `anon`, `authenticated`, `service_role`). Первая миграция содержит явные grants для каждой public-таблицы: authenticated SELECT, service_role ALL, client DML и anon-доступ запрещены. Прикладные записи выполняются через RPC. Private-схема не должна быть открыта через Data API.

Нужно проверить в target: доступность `xid8`/`pg_current_xact_id()`, `gen_random_uuid()`, `hashtextextended()`, IANA timezone database, PLpgSQL, стандартных Auth-объектов и прав migration executor. Это встроенные возможности поддерживаемых современных PostgreSQL; наличие `gen_random_uuid()` не означает обязательную установку pgcrypto. Не устанавливать расширения наугад.

`xid8`/`pg_current_xact_id()` требуют PostgreSQL 13+, но это нижняя граница отдельной зависимости, не доказательство совместимости всего пакета со всеми версиями 13+. SECURITY DEFINER-функции получают владельца от роли применения: пакет не задаёт ALTER OWNER. Необходимо проверить, что исполнитель/владелец имеет нужный доступ к Auth и контролируемым записям. При фиксированном search_path `pg_catalog, public` не допускать CREATE в public для недоверенных ролей.

**Особое условие безопасности grants:** явные REVOKE для authenticated снимают INSERT/UPDATE/DELETE, но не TRUNCATE/REFERENCES/TRIGGER и не потенциальный доступ через PUBLIC/членство в других ролях. На target с расширенными default privileges это может оставить опасные права; RLS не защищает TRUNCATE. До применения/открытия API нужна проверка эффективных и default grants. Если обнаружится такой доступ, применение безопасным не считать; исправление согласовать отдельно, не переписывая девять утверждённых файлов. Статический аудит не доказывает наличие этой проблемы в неподтверждённом target.

Предыдущие локальные проверки выполнены на PostgreSQL 17.11. Они не подтверждают версию target, реальную структуру Auth, default privileges, поведение PostgREST, владельцев SECURITY DEFINER или hosted доступность RPC. Фактическая версия и содержимое target в этом этапе не проверялись: метаданные подключения их не возвращают, любой SQL запрещён. SHA-256 девяти миграций и девяти rollback совпадают с предыдущей подготовительной проверкой.

## 4. Дополнительные настройки для следующих этапов

- **Auth:** проверить текущий статус регистрации, не включать её сейчас; позднее согласовать email confirmation, парольную политику, rate limits, SMTP, Site URL и точный redirect allowlist для тестовых адресов. Фактический статус этих настроек неизвестен.
- **Профиль:** девять миграций не создают signup provisioning trigger. Нужна отдельно утверждённая новая миграция с транзакционным созданием profiles; исходные девять не переписывать. До этого регистрация не готова.
- **Data API:** проверить включение API и доступность public, не добавлять shiftly_private в exposed schemas; не расширять owner grants ради устранения ошибки доступа.
- **Ключи:** публичные URL/publishable key отдельно от server-only service_role/secret key; привязка всех значений к одному подтверждённому test ref. Никогда не помещать привилегированный ключ в VITE_* или клиентский код. В этом этапе ключи не запрашивались и не менялись.
- **Серверные вызовы:** дальнейшая реализация — проверяемый bearer пользователя и RPC с owner-derived identity; server-only привилегии лишь для согласованных задач. Никакой реализации в этом этапе.
- **Автоматизация:** отдельно настроить доверенный scheduler закрытия локальных месяцев и очистки корзины, мониторинг ошибок и backup retention; пакет не устанавливает расписание. pg_cron/pg_net нужны только при выборе соответствующего механизма, а не для базовых девяти миграций.
- **Нерешённые операции:** исторический `confirm_history` и смена timezone с историей остаются безопасно запрещёнными до утверждения политики; не обходить эти guards при интеграции.
